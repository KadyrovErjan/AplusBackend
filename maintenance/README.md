# Maintenance: как это работает

## Что такое `maintenance`

`maintenance` в этом проекте отвечает не за весь ремонтный контур целиком, а именно за фиксацию заявок о поломках от водителей.

По сути это слой, который:

1. принимает сообщение о проблеме от водителя;
2. привязывает проблему к водителю и его текущей технике;
3. группирует несколько сообщений в одну активную заявку на ремонт;
4. сохраняет фото;
5. создаёт уведомление для администраторов;
6. отдаёт список и детали заявок для сайта / панели.

Самого кода Telegram-бота в этом репозитории нет. Здесь видна backend-часть, которую бот вызывает.

## Основные сущности

### `IssueReport`

Главная заявка на ремонт.

Содержит:

- `driver` — водитель;
- `vehicle` — техника;
- `description` — последнее актуальное описание;
- `status` — `pending`, `in_progress`, `resolved`;
- `created_at` — когда заявка была впервые открыта;
- `resolved_at` — когда закрыта;
- `last_problem_at` — когда по ней пришла последняя проблема.

Важная бизнес-логика:

- на одного водителя и одну технику может быть только одна активная заявка со статусом `pending` или `in_progress`;
- это ограничено на уровне БД через `UniqueConstraint`.

### `IssueReportProblem`

Это отдельная проблема внутри заявки.

Если водитель несколько раз пишет в бот про одну и ту же технику, система не всегда создаёт новую заявку. Часто она добавляет новый `IssueReportProblem` внутрь уже существующего `IssueReport`.

Именно поэтому одна заявка может содержать историю из нескольких сообщений водителя.

### `IssueReportPhoto`

Фото, привязанное:

- к заявке `IssueReport`;
- при наличии ещё и к конкретной проблеме `IssueReportProblem`.

То есть фото могут быть связаны не просто с ремонтом в целом, а с конкретным сообщением о проблеме.

## Поток от Telegram-бота до заявки

Основной вход для бота:

- `POST /api/maintenance/issues/`

Ожидаемые данные:

- `telegram_id`
- `description`
- `photos[]` — необязательно, multipart upload

Пример payload:

```json
{
  "telegram_id": 999111,
  "description": "Пробита шина"
}
```

### Что backend делает по шагам

1. Берёт `telegram_id` и `description` из запроса.
2. Ищет пользователя с таким `telegram_id` и ролью `driver`.
3. Ищет активное назначение техники через `VehicleAssignment`, где `unassigned_at IS NULL`.
4. Если у водителя нет активной техники, возвращает ошибку `driver_has_no_vehicle`.
5. В транзакции ищет уже существующую активную заявку `IssueReport` для пары `driver + vehicle` со статусом `pending` или `in_progress`.
6. Если активной заявки нет, создаёт новую.
7. Если заявка уже есть, не дублирует её, а использует существующую.
8. Создаёт новый `IssueReportProblem` с текстом текущей проблемы.
9. Прикрепляет все загруженные фото к этому `IssueReportProblem`.
10. Обновляет у `IssueReport` поля:
    - `description` = последнее описание;
    - `last_problem_at` = время последней проблемы.
11. Создаёт внутреннее уведомление для администраторов через `send_notification(...)`.

Ответ:

```json
{
  "status": "ok",
  "report_id": 12,
  "created_new": true,
  "problem_id": 44
}
```

### Что важно понимать

- `IssueReport` здесь работает как "контейнер активного ремонта".
- `IssueReportProblem` — как отдельные сообщения внутри этого ремонта.
- повторные сообщения по той же технике не плодят новые активные записи без необходимости.

## Как `maintenance` связан с Telegram-ботом

### Что делает бот

Судя по backend-коду, бот должен:

- знать `telegram_id` пользователя;
- отправить описание проблемы;
- при необходимости отправить фото;
- вызвать backend endpoint `/api/maintenance/issues/`.

### Что делает backend

Backend:

- не читает Telegram напрямую;
- не поднимает Telegram webhook внутри `maintenance`;
- не определяет пользователя по сессии;
- использует именно `telegram_id`, пришедший в payload.

Это означает, что связка с Telegram здесь построена как:

`Telegram bot -> HTTP запрос в Django backend -> maintenance logic`

### Что важно не перепутать

Для `maintenance` уведомление админам создаётся через внутреннюю систему `notifications`, а не через прямую отправку сообщения в Telegram.

То есть при создании заявки вызывается:

- `services.notification_service.send_notification(...)`

Эта функция создаёт записи `Notification` для администраторов в базе.

## Где в проекте есть прямой Telegram outbound

Прямой выход в Telegram есть в другом месте:

- `services/admin_telegram.py`

Там backend уже сам стучится в bot API по `BOT_API_URL` и отправляет сообщения администраторам на endpoint:

- `/internal/notify-admin`

Но это используется для других событий:

- старт смены;
- завершение смены;
- включение зажигания;
- долгий простой техники.

Для `maintenance` такой прямой отправки в Telegram сейчас не видно. Здесь только создание внутренних уведомлений в БД.

## Связанные модули

### `users`

Telegram сильно завязан на app `users`.

Через него происходят:

- регистрация водителя из Telegram: `POST /api/users/full_register/`;
- привязка Telegram к админу: `POST /api/users/telegram/admin/start/`;
- получение профиля по `telegram_id`: `GET /api/users/profile/<telegram_id>/`;
- старт и завершение смены через бот.

Именно `users.CustomUser.telegram_id` является ключом, по которому `maintenance` понимает, кто отправил сообщение.

### `vehicles`

`maintenance` опирается на `VehicleAssignment`.

Ключевая идея:

- если водитель не назначен на технику, ремонтную заявку создать нельзя;
- техника в заявке определяется не из payload, а из текущего активного назначения в БД.

Это хороший защитный механизм: бот не сообщает `vehicle_id` напрямую, backend сам вычисляет актуальную машину водителя.

### `notifications`

После создания заявки формируется `Notification` типа `service`.

Дальше эти уведомления можно получать через:

- `GET /api/notifications/`

То есть администраторская часть сайта может показать новый ремонтный инцидент без Telegram.

### `reports`

`maintenance` участвует и в отчётах:

- в годовом отчёте считается количество заявок `IssueReport` по технике;
- есть Excel-выгрузка заявок на ремонт.

## Как работает список заявок

Endpoint:

- `GET /api/maintenance/issues/`

Поведение:

- заявки сортируются по `-last_problem_at`, потом по `-created_at`;
- можно фильтровать по `status`;
- на карточку отдаются:
  - `id`
  - `status`
  - `preview_photo`
  - `vehicle`
  - `driver`

### Откуда берётся `preview_photo`

Логика превью такая:

1. сначала берётся первая проблема `problems[0]`;
2. затем первая её фотография;
3. если такого фото нет, берётся первое фото заявки в целом;
4. если фото нет совсем, возвращается `null`.

## Как работает детальная страница заявки

Endpoint:

- `GET /api/maintenance/issues/<id>/`

Отдаёт:

- дату создания;
- статус;
- описание;
- фото;
- технику;
- водителя;
- список проблем.

### Нестандартная особенность

Детальная сериализация показывает не все `IssueReportProblem`, а только те, которые были созданы в тот же локальный день, что и сама заявка `IssueReport`.

То есть используется логика "open day":

- берётся `localdate(report.created_at)`;
- в `problems` попадают только записи с той же датой;
- остальные, созданные в следующие дни, в detail API не попадут.

Это важно, потому что:

- в модели одна заявка может жить дольше одного дня;
- новые проблемы могут добавляться позже;
- но detail endpoint сейчас фактически показывает только проблемы дня открытия заявки.

### Ещё один нюанс

Поле `IssueReport.description` при новых сообщениях обновляется последним текстом проблемы.

Но detail serializer старается показывать:

- описание первой проблемы дня открытия, если такие проблемы есть;
- иначе fallback на `IssueReport.description`.

Из-за этого:

- в списке и в базе описание заявки может быть "последним";
- в detail API описание может быть "первым за день открытия".

Для поддержки и фронта это важная особенность.

## Как закрывается или меняется статус ремонта

В `maintenance` нет отдельного API, который переводит заявку в `in_progress` или `resolved`.

В коде репозитория видно:

- модель поддерживает эти статусы;
- Django admin позволяет их менять;
- тесты проверяют сценарий, где старая заявка уже `resolved`, и после этого создаётся новая.

Практически это выглядит так:

- пока заявка `pending` или `in_progress`, новые сообщения водителя складываются в неё;
- когда заявка становится `resolved`, следующее сообщение создаёт уже новый `IssueReport`.

## Что проверено тестами

Тесты `maintenance/tests.py` подтверждают ключевое поведение:

- активная заявка переиспользуется для той же пары `driver + vehicle`;
- после `resolved` создаётся новая заявка;
- без активной техники возвращается ошибка;
- обработан race condition при конкурентном создании;
- список отдаёт карточки с превью;
- detail API работает с "open day" логикой;
- legacy-заявки без `IssueReportProblem` всё ещё поддерживаются.

## Ограничения и наблюдения

### 1. `maintenance` не переводит технику автоматически в статус `repair`

В текущем коде создание `IssueReport` не меняет `Vehicle.status`.

То есть факт заявки на поломку и фактический статус техники живут отдельно.

### 2. Нет прямого Telegram-уведомления о новой поломке

По крайней мере в текущем backend-коде новая ремонтная заявка создаёт запись `Notification`, но не вызывает `services.admin_telegram.send_to_admins`.

### 3. Идентификация строится на `telegram_id`

Endpoint бота не использует авторизацию через JWT как обязательный источник пользователя. Он принимает `telegram_id` в теле запроса и по нему находит водителя.

### 4. Активная техника определяется backend-ом

Это плюс для консистентности, но значит, что вся цепочка зависит от корректного `VehicleAssignment`.

Если назначение неактуально, бот создаст заявку не туда или не создаст вовсе.

## Кратко

`maintenance` в этом проекте — это backend-механизм учёта поломок от водителей, пришедших в основном из Telegram-бота по `telegram_id`.

Бот здесь выступает как клиент, а не как место хранения логики. Основная логика живёт в Django:

- поиск водителя;
- определение его текущей техники;
- защита от дублей активных заявок;
- накопление нескольких проблем внутри одной заявки;
- сохранение фото;
- уведомление админов через внутреннюю систему уведомлений.
