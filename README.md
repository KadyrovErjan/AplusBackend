# APlus Backend

## Что это за проект

`APlus Backend` — это Django backend для внутренней системы управления автопарком и водителями.

По коду видно, что проект решает сразу несколько бизнес-задач:

- учёт техники и её текущего статуса;
- регистрация и сопровождение водителей;
- работа с Telegram-ботом как с внешним клиентом;
- контроль смен;
- учёт рейсов;
- учёт заправок и топливных событий;
- заявки на ремонт;
- уведомления для администраторов;
- Excel-отчёты по технике, ремонтам, заправкам, рейсам и годовой аналитике;
- realtime-обновления по технике через WebSocket.

Проект не является просто CRUD-приложением. Внутри есть и API, и фоновые задачи, и интеграция с GPS/телематикой Incomtek/Pilot, и отдельный polling worker.

## Технологический стек

Основной стек:

- Python 3.12
- Django 5.2
- Django REST Framework
- SimpleJWT
- PostgreSQL
- Redis
- Celery + Celery Beat
- Channels + Daphne
- WebSocket
- drf-yasg / Swagger
- openpyxl
- aiohttp / requests

Инфраструктурно проект запускается через:

- `backend` — ASGI-приложение на Daphne;
- `worker` — отдельный polling worker;
- `celery` — фоновые задачи;
- `celery-beat` — расписание;
- `db` — PostgreSQL;
- `redis` — брокер / channel layer;
- `nginx` — reverse proxy и SSL.

## Общая архитектура

На уровне логики проект можно представить так:

```text
Telegram Bot / Frontend / Admin
            |
            v
      Django REST API
            |
            +--> PostgreSQL
            +--> Redis
            +--> Celery tasks
            +--> WebSocket updates
            +--> Incomtek / Pilot API
            +--> Bot API для уведомлений админов
```

Есть три ключевых способа движения данных:

1. Синхронный HTTP API для фронта, бота и админских операций.
2. Фоновые задачи и polling для периодической синхронизации.
3. WebSocket-поток для live-обновлений техники.

## Основные приложения

### `users`

Отвечает за пользователей и Telegram-сценарии.

Здесь находятся:

- кастомная модель `CustomUser`;
- роли: `driver`, `mechanic`, `admin`;
- статусы водителя: `registration`, `pending_vehicle`, `active`;
- обычная регистрация и логин;
- Telegram-регистрация водителя;
- привязка Telegram к админу;
- профиль пользователя по `telegram_id`;
- старт и завершение смены;
- часть логики KPI по сменам.

Это один из центральных app проекта, потому что через него проходит почти вся идентификация водителей из Telegram.

### `vehicles`

Главный app по технике.

Содержит:

- модель `Vehicle`;
- назначение водителя на технику через `VehicleAssignment`;
- смены водителей через `DriverShift`;
- статус техники, координаты, топливо, пробег, моточасы;
- историю аренды;
- историю телематического статуса;
- dashboard и карточки техники;
- WebSocket-роуты и consumer для realtime-обновлений.

`vehicles` является базой почти для всех остальных модулей: рейсы, ремонты, заправки, уведомления и отчёты все так или иначе ссылаются на технику.

### `maintenance`

Отвечает за заявки на ремонт.

Основные сущности:

- `IssueReport` — сама заявка на ремонт;
- `IssueReportProblem` — отдельная проблема внутри заявки;
- `IssueReportPhoto` — фото по заявке или конкретной проблеме.

Ключевая идея:

- водитель через Telegram-бота сообщает о проблеме;
- backend находит его по `telegram_id`;
- backend определяет текущую технику через `VehicleAssignment`;
- если по этой технике уже есть активная заявка, новая проблема добавляется в неё;
- если заявка закрыта, создаётся новая.

Подробный разбор вынесен в [maintenance/README.md](./maintenance/README.md).

### `fuels`

Отвечает за топливо и связанные подтверждения.

Содержит:

- `FuelEvent` — события заправки/слива из внешней системы;
- `FuelConfirmation` — подтверждение заправки от водителя;
- `FuelReport` — ручной / пользовательский отчёт;
- `FuelZone` — топливные геозоны / объекты.

Внутри есть логика:

- импорта топлива из Incomtek;
- геозон;
- сопоставления событий с водителем и техникой;
- подтверждения заправки водителем;
- аналитики по заправкам.

### `trips`

Отвечает за рейсы.

Основная сущность:

- `Trip` — рейс техники между зонами.

Сейчас в проекте видно, что:

- исторический модуль рейсов остался активным;
- часть старой периодической синхронизации отключена;
- при завершении смены всё ещё запускается пересчёт / синхронизация данных по машине;
- данные о рейсах используются в отчётах и в сверке со сменами.

### `notifications`

Внутренняя система уведомлений для администраторов.

Через неё создаются уведомления о:

- низком топливе;
- сервисных событиях;
- заявках на ремонт;
- регистрации водителей;
- предупреждениях;
- информационных событиях по сменам.

Это именно внутренняя база уведомлений, которую потом можно читать через API.

### `reports`

Отвечает за Excel-отчёты.

Есть выгрузки:

- по технике;
- по ремонтам;
- по заправкам;
- по рейсам;
- по сводной годовой аналитике.

`reports` агрегирует данные сразу из нескольких app:

- `vehicles`
- `maintenance`
- `fuels`
- `trips`

### `services`

Технический и интеграционный слой.

Здесь находятся:

- клиент к Pilot/Incomtek API;
- polling worker;
- отправка Telegram-уведомлений администраторам;
- парсеры внешних данных;
- сервисные функции по уведомлениям и поездкам.

Это не самостоятельный доменный модуль, а инфраструктурная прослойка между app и внешними системами.

### `common`

Небольшой общий код, например вспомогательные сериализаторы и функции для файловых URL.

## Основные сущности домена

Если смотреть сверху вниз, картина проекта такая:

### Пользователь

Пользователь хранится в `users.CustomUser`.

Важные поля:

- `email`
- `telegram_id`
- `telegram_username`
- `role`
- `status`
- документы и селфи для водителя

### Техника

Техника хранится в `vehicles.Vehicle`.

Важные поля:

- `veh_id`
- `imei`
- `name`
- `plate_number`
- `status`
- `lat`, `lon`, `speed`
- `fuel`
- `mileage`
- `total_engine_hours`

### Назначение техники

Связь водитель <-> техника идёт через `VehicleAssignment`.

Это очень важный слой, потому что:

- через него определяется текущая машина водителя;
- на него завязаны ремонты;
- на него завязаны смены;
- он участвует в отображении актуального водителя у техники.

### Смена

Смена хранится в `vehicles.DriverShift`.

С ней связаны:

- водитель;
- техника;
- время старта и завершения;
- количество рейсов со слов водителя;
- фактическая дистанция;
- late / worked metrics;
- idle monitoring.

### Рейс

Рейсы хранятся в `trips.Trip`.

Они используются для истории, статистики и сверки со сменами.

### Ремонт

Ремонтные инциденты хранятся в `maintenance`.

Они связаны с:

- водителем;
- техникой;
- фото;
- внутренними уведомлениями.

### Топливо

Топливный контур состоит из:

- событий датчика;
- подтверждений водителя;
- пользовательских отчётов;
- геозон / объектов.

## Как Telegram встроен в проект

Telegram здесь важен, но сам бот в этом репозитории не лежит.

По коду видно два основных сценария.

### 1. Бот как клиент backend

Бот отправляет запросы в Django backend для:

- регистрации водителя;
- привязки Telegram к админу;
- получения профиля;
- начала смены;
- завершения смены;
- создания заявок на ремонт;
- отправки отчётов по топливу.

В большинстве таких сценариев backend определяет пользователя по `telegram_id`.

### 2. Backend как клиент bot API

В `services/admin_telegram.py` backend может сам отправлять сообщения администраторам через внешний bot API.

Это используется для событий вроде:

- старт смены;
- завершение смены;
- включение зажигания;
- долгий простой техники.

То есть Telegram здесь двусторонний канал, но с разными точками ответственности.

## Интеграция с Incomtek / Pilot

Это одна из ключевых частей проекта.

Из внешней системы проект получает:

- телеметрию техники;
- статусы и координаты;
- топливо;
- пробег;
- моточасы;
- отчёты по поездкам / маршрутам / пробегу.

Основные файлы:

- `services/pilot_client.py`
- `services/pilot_parsers.py`
- `services/polling_worker.py`

### Как это работает

1. Отдельный polling worker периодически запрашивает данные по всей технике.
2. Данные обновляют записи `Vehicle`.
3. При необходимости сохраняется `VehicleStatusHistory`.
4. Данные публикуются в WebSocket-группы.
5. На основе изменений могут рождаться топливные события и предупреждения.
6. Параллельно Celery-задачи и сервисы используют отчёты Incomtek для аналитики, топлива и смен.

## Realtime-слой

Проект использует Django Channels.

WebSocket endpoints:

- `ws/vehicles/`
- `ws/vehicles/<vehicle_id>/`

Для подключения нужен JWT-токен в query string.

Через WebSocket клиент получает live-обновления по технике:

- координаты;
- скорость;
- зажигание;
- топливо;
- статус.

## Фоновые процессы

В проекте есть несколько разных типов фоновой работы.

### Polling worker

Запускается как отдельный процесс:

- `python -m services.polling_worker`

Он:

- регулярно обходит всю технику;
- тянет данные из Pilot;
- обновляет состояние техники;
- пишет историю;
- рассылает WebSocket update;
- может регистрировать топливные события;
- может создавать предупреждения.

### Celery tasks

По коду и расписанию в `settings.py` запускаются задачи:

- проверка низкого топлива;
- проверка необходимости ТО;
- импорт топлива;
- синхронизация техники;
- мониторинг авто-создания смен;
- контроль простоя техники;
- синхронизация по закрытию смены.

### Celery Beat

Отвечает за расписание регулярных задач.

## Авторизация и безопасность

Проект использует:

- cookie-based JWT authentication для API;
- SimpleJWT;
- refresh/access токены;
- CORS-настройки для фронтенда;
- secure cookie settings для production;
- Sentry в production;
- отдельный секрет для привязки админа через Telegram: `ADMIN_TELEGRAM_SECRET`.

При этом часть Telegram-endpoint'ов завязана не на пользовательскую сессию, а на входной `telegram_id`.

## Потоки данных по бизнес-сценариям

### Регистрация водителя через Telegram

```text
Telegram Bot
  -> /api/users/full_register/
  -> создаётся или обновляется CustomUser
  -> создаётся VehicleRequest
  -> админам создаются уведомления
```

### Подтверждение водителя и назначение техники

```text
Admin
  -> approve request
  -> user.status = active
  -> создаётся VehicleAssignment
```

### Начало смены

```text
Telegram Bot
  -> /api/users/shifts/start/
  -> backend находит driver по telegram_id
  -> находит текущую технику
  -> создаёт DriverShift
```

### Завершение смены

```text
Telegram Bot
  -> /api/users/shifts/end/
  -> закрывается DriverShift
  -> сохраняется trips_count
  -> запускается sync_single_vehicle_task
  -> админам создаётся уведомление
```

### Заявка на ремонт

```text
Telegram Bot
  -> /api/maintenance/issues/
  -> backend находит driver и его vehicle
  -> создаёт или дополняет IssueReport
  -> создаёт Notification
```

### Обновление карты техники

```text
Pilot / Incomtek
  -> polling_worker
  -> Vehicle / VehicleStatusHistory
  -> WebSocket group
  -> frontend получает realtime update
```

## Как проект запускается в Docker

Основной сценарий из `docker-compose.yml`:

1. Поднимается PostgreSQL и Redis.
2. Backend выполняет:
   - `migrate`
   - `collectstatic`
   - `fill_plate_numbers`
   - `sync_vehicles`
   - запуск Daphne
3. Отдельно поднимается polling worker.
4. Отдельно поднимаются `celery` и `celery-beat`.
5. Снаружи всё обслуживает `nginx`.

## Что важно понимать новому разработчику

### 1. Это не чисто REST-проект

Здесь значительная часть логики живёт не только во view:

- в Celery tasks;
- в polling worker;
- в сервисах интеграции;
- в моделях и сериализаторах;
- в WebSocket consumer.

### 2. `telegram_id` — важный ключ домена

Много сценариев строится не вокруг обычной веб-сессии, а вокруг Telegram-идентификатора пользователя.

### 3. `VehicleAssignment` — одна из центральных связей

Если назначение техники неверно, могут ломаться:

- смены;
- ремонты;
- топливные подтверждения;
- отображение актуального водителя.

### 4. Часть логики зависит от внешних данных

Без корректной работы Incomtek / Pilot часть функций проекта не сможет полноценно работать:

- realtime;
- топливо;
- пробег;
- моточасы;
- аналитика по сменам;
- часть отчётов.

### 5. В проекте есть смесь старых и новых контуров

По коду видно, что часть функциональности развивалась итеративно:

- есть legacy-сценарии и legacy-таблицы;
- часть синхронизаций отключена или заменена;
- есть разные способы получения похожих данных.

Это нужно учитывать при рефакторинге.

## Краткое резюме

Этот backend объединяет несколько контуров в одной системе:

- управление людьми;
- управление техникой;
- телематику;
- Telegram-бота;
- ремонты;
- заправки;
- уведомления;
- отчётность.

Архитектурно это Django-монолит с выраженным интеграционным и асинхронным слоем:

- REST API для клиентов;
- WebSocket для карты и live-статусов;
- Celery для фоновых задач;
- polling worker для внешней телематики;
- PostgreSQL как основное хранилище;
- Redis как транспорт и брокер.
